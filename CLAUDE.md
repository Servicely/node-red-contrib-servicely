# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Node-RED plugin (`node-red-contrib-servicely`, published to npm and the Node-RED palette) giving nodes for integrating with Servicely.ai: the asynchronous queue/actions API, data imports/transforms, the REST API and Inbound Webhooks. Plain CommonJS JavaScript with no build step and **no runtime dependencies** (HTTP uses the built-in `fetch`, hashing uses `node:crypto`). Requires Node >= 18 and Node-RED >= 3. User docs: https://docs-servicely.atlassian.net/wiki/spaces/SD/pages/2247196673/Node-RED

## Public repository

This repository is **public** (it is mirrored to GitHub and published to npm). Everything committed here must be safe to publish. That applies to code, docs, commit messages and branch names. Never include:
- internal ticket or issue-tracker IDs or links;
- customer or partner names;
- internal wiki or Confluence links, other than the public user docs linked above;
- hostnames, credentials or tokens, including ephemeral test ones;

Describe changes by what they do, e.g. "Replace request with fetch", not by ticket. Internal notes or handoff documents belong outside the repo, or under a path excluded in `.git/info/exclude` (such as `docs/internal/`), never in a tracked file.

## Development

```sh
npm test                                   # mocha specs in test/ (node-red-node-test-helper, real Node-RED runtime)
npx mocha test/rest_spec.js -g "webhook"   # a single spec file / tests matching a name
npm run lint                               # ESLint (flat config), including inline <script> in *.html
```

Specs run the nodes against a local mock server (`test/helpers/mock-server.js`); they never need a Servicely instance. CI (`.github/workflows/test.yml`) runs lint + tests on Node 20-24 against Node-RED 4 and 5.

For manual testing, `docker_run.sh` starts `nodered/node-red` (version via `NR_VERSION`, default pinned) with the repo mounted at `/plugin`; install it once with `docker exec -it nodered bash -c "cd /data && npm i --save node-red-contrib-servicely@/plugin"`. See README_DEVELOPER.md. Release: bump `version`, update CHANGELOG.md, `npm pack --dry-run` (the `files` whitelist controls what is published), then `npm publish .`.

## Architecture

Each `servicely-*.js` runtime file is paired with a `servicely-*.html` editor file (node definitions, edit forms, help text). The `node-red.nodes` map in `package.json` registers the four runtime modules, and each module registers one or more node types:

- **servicely-connection.js**: `servicely-connection` config node (`baseUrl`, `queue`, `authtype`: `password` | `token_hmac_header` | `bearer`). Secrets are Node-RED **credentials** named `user`, `pass`, `apiToken`, `apiSecret`, and the runtime exposes them as `username`/`password`/`token`/`secret`. `servicely-connection-injector` sets `msg._connectionNode`.
- **servicely-queue.js** (palette `servicely`): `servicely-queue` dequeues from `controller/AsyncIntegration`. Queue nodes sharing a connection and polling interval share a `Poller` (`node.poller`), so each round is one combined dequeue (Servicely 1.11.122 or later; `subjects: [{subject, request_count, identifier}]`) routed to the nodes by each action's `subject`. The request's `subject` is a sentinel (`__node-red-combined__`) and it also sends a top-level `identifier` (older builds reject a dequeue without one), so an instance without combined dequeues claims nothing. The instance takes at most 50 subjects and 1,000 actions per call, so a round is split into several requests, and one subject's count is capped at 1,000. Its errors carry `_error` only. Its response has no `subjects` marker object, and the poller then falls back to one dequeue per node (`mode` `legacy`), retrying the combined form hourly. A round is scheduled with `setTimeout` only after the previous one completes (`inFlight` guard), with an immediate round for the nodes that got a full batch, and closing waits for a round in flight. Each action becomes a message carrying `msg.parts` (`id`/`type: "array"`/`index`/`count`, so it is Join-compatible). `servicely-success` / `-failure` / `-progress` share `replyHandler` and post replies correlated by `msg._reply_to`. Progress sends `msg.progress` or the configured message, and passes the message on only after the instance accepts it: the instance applies replies in arrival order, and any reply to a finished action reopens it (a late Progress strands it as *pending*). A non-zero `msg.rc.code` replies with `msg.rc.message`. Replies send an object or array payload as JSON text (Intelligent Actions reject anything else), `identifier` from `msg._original_payload.claimed_by`, and Failure adds `error` (the caught `msg.error.message`, else the payload), which the instance uses as the description. An unknown `_reply_to` gets a 500 script error. A message without `_reply_to` (e.g. a dequeue error, marked `msg._dequeue_error`, passed on by Catch) is skipped with a rate-limited warning and no error, so Catch → Failure can't loop; Progress still passes it on.
- **servicely-rest.js** (palette `servicely-rest`): `servicely-rest` calls `baseUrl + renderUri(uri, msg)`. `output_mode` `auto` returns `body.data` when present, otherwise the whole body (Inbound Webhook v2 responses aren't wrapped in `data`). `servicely-import` / `servicely-transform` POST to `controller/ImportManager` and write results to `msg.import_result` / `msg.transform_result`, leaving `msg.payload` untouched. They are skipped when `msg.import_enabled` / `msg.transform_enabled` is `false`. The instance reports a failed import or transform (including row failures) as `success: false` in a 200, which the nodes turn into an error after storing the result; it answers an unknown name with a 500 script error that doesn't say which name. `import_data` and `import_metadata` must be JSON strings of arrays, so a single row object is wrapped. Import sets `msg.import_table`, and `msg.transform_name` from its own *Transform* field (never sent to the instance), so a Transform node after it needs no settings. Transform refuses to run without both names, since the instance doesn't fall back to the transform's default table. Both take the same token override as the Webhook node (see *Token overrides*); signed headers other than `Date` come from `msg.headers`, and only those are sent. The module also registers the import/transform discovery and Test auth routes.
- **servicely-webhook.js** (palette `servicely-rest`): `servicely-webhook` calls an Inbound Webhook V2, `/_webhook/v2/{key}`. The key is a Key or id (with `${msg.x}` placeholders), or `msg.webhook_key`. `msg.webhook_params` becomes the query string and `msg.headers` becomes extra headers; auth headers can't be overridden that way. Auth is the connection's, or a node-level override, because a webhook can be locked to one ApiToken. The override can be `bearer`, `token_hmac_header` or `token_hmac_body`; its token and secret are the node's credentials (`apiToken`/`apiSecret`), and `hash_method` and `signed_headers` (default `Date`) must match the token's settings. The body is serialised once and sent as `body`, so HMAC body signing covers the exact bytes. Query values encode spaces as `%20`, not `+`, so the URL-decoded URI that gets signed is unambiguous. The whole body goes to `msg.payload`, with a summary in `msg.webhook` (`key`, `skipped`, `reason`, `operation`, `table`, `recordId`, `warnings`). `skip_output` routes `{skipped:true}` responses to a second output. The module also registers the webhook discovery routes (see below).
- **servicely-common.js**:
  - `sendRequest`: a `fetch` wrapper with an `(err, res, body)` callback. The request body is `json` (serialised) or `body` (an already-serialised string). It has a 30s timeout and no cookie jar. The body is parsed JSON or the raw text, and parsing never throws.
  - `describeHttpError`: turns an error response into text, including `_error` / `_errorId`.
  - `generateHeaders(auth, request)`: Basic, Bearer, or `Authorization: HMAC <token>:<base64 signature>` plus `Date`, where `auth` is a connection or a plain object. HMAC uses `auth.hashMethod` (md5/sha1/sha256/sha512, default sha256).
    - `token_hmac_header` signs the values of `auth.signedHeaders`, default `["Date"]`, joined with `:`.
    - `token_hmac_body` signs `METHOD\nContent-MD5\nContent-Type\nDate\nURL-decoded path+query` and sends `Content-MD5`. It needs `request` = `{method, url, body}`, with `body` the exact JSON string sent.
    - It throws when it can't sign, e.g. a signed header is missing (`err.signedHeader`).
    - Connections always sign `Date` with SHA-256.
  - `resolveAuthType`: infers the auth type for legacy connections saved without one.
  - `renderUri`: `${msg.x}` / `<%= msg.x %>` substitution. Values are URL-encoded (or by an optional `encode` function), and only plain property paths are allowed.
  - Node helpers shared by every HTTP node: `getConnection` (node config, else `msg._connectionNode`), `reportError` (status, `msg.payload`, `msg.statusCode`, `done(err)`) and `performRequest`. `performRequest`'s `onSuccess(body)` may return what to `send` (an array for several outputs) and is exception-safe. It also takes options: `describeHttpError` and `allowText`.
  - Token overrides: `overrideAuth`, `nodeAuth(node, config, connection)` (throws when the token or secret is missing) and `signedExtraHeaders`.
  - `registerDiscoveryRoute`, `relayToEditor`, `registerAuthTest` and `dialogCredential`: editor-time lookups and Test auth (see *Instance discovery*).
- **resources/servicely-editor.js**: editor code shared by the dialogs, `window.ServicelyEditor`. Each HTML file loads it with `<script src="resources/node-red-contrib-servicely/servicely-editor.js">` before registering. It holds the validators, the Auth rows (`dialog(node)`: auth mode, lookups, Test auth), the saved-details helpers (`snapshot`, `snapshotToSave`), table and mapping renderers, and the shared CSS (`servicely-*` classes). Templates use the same element ids for these parts (`node-input-authmode`, `node-input-servicely-message`, `node-input-servicely-test`, …), so a new node copies the markup and calls the helpers.

### Conventions that span files

- **Token overrides.** Nodes that call the instance for a user's flow (Webhook, Import, Transform) can use their own API token instead of the connection's: `defaults` from `ServicelyEditor.authDefaults()` (`authmode` `connection` | `bearer` | `token_hmac_header` | `token_hmac_body`, `hash_method`, `signed_headers`), credentials `apiToken` / `apiSecret` registered on the runtime type, `common.nodeAuth` at runtime, and a Test auth route. Serialise the body once and pass it to `generateHeaders` so HMAC body signing covers the bytes sent.
- **Field prompts.** Every edit-form field has a one-line `<div class="servicely-hint">` inside its `form-row` (styled by `resources/servicely-editor.js`, which every HTML file loads) saying what it is for and where a blank value comes from. The help panel holds the full explanation.
- **Misconfigured nodes.** Mark invalid settings with `validate` functions in the editor's `defaults`.
  - Validators take `(value, opt)` and return `opt ? reason : false`: the reason shows on Node-RED 3.1+, and 3.0 gets a plain `false`.
  - Don't make a field `required` when the message can supply it (`msg._connectionNode`, `msg.webhook_key`, …).
  - Credentials are only loaded once the dialog opens, so validate them through a `defaults` property using `this.credentials` (`has_<name>` or the typed value), and treat `this.credentials` undefined as valid.

- Errors go through `done(err)` (or `node.error(text, msg)` where no input message exists) with the message attached, so **Catch** nodes receive them. HTTP errors also set `msg.statusCode`. Every HTTP callback must be crash-safe: an exception inside an async callback terminates the whole Node-RED runtime.
- Nodes share context through underscore-prefixed `msg` fields, which must survive intermediate nodes: `_connectionNode` (connection config node id), `_reply_to` (queue action id), `_original_payload` (the raw dequeued item).
- Never put credentials in URLs (`fetch` rejects them anyway). Auth only goes in headers.
- **Legacy-flow compatibility.** The editor only keeps properties listed in `defaults` when it re-saves a node, so the legacy plain-text `username` / `password` / `token` / `secret` stay declared (hidden) in `servicely-connection.html`. `oneditprepare` copies them into the credential inputs, and `oneditsave` clears them. Don't remove those defaults, or existing flows lose their credentials on the next full deploy.

### Instance discovery (editor-time)

Editors can read lists and configuration from the instance (webhooks, import tables and transforms; REST next) so users can pick instead of type. The same rules apply to every new lookup:

- **Admin routes, server-side credentials.** Register each lookup with `common.registerDiscoveryRoute(RED, route, upstreamPath, unsupportedMessage)`. It serves `GET /servicely/:connection/<route>`, guarded by `RED.auth.needsPermission("servicely-connection.read")`, and calls the instance with the **deployed** connection's `generateHeaders`. Credentials never reach the browser. An undeployed connection gives a 404 telling the user to deploy it first. Discovery always uses the connection's credentials, never a node's token override.
- **Dedicated read-only endpoints, never the generic `/v1` table API.** Each lookup uses an instance endpoint with a trimmed, stable contract (`{"data": ...}`, errors as `{_error, _errorId}`). Endpoints sit beside their feature's own API: webhooks use `GET /_webhook_admin/v2/inbound[/{idOrKey}]`, and imports/transforms use `GET /_import_admin/v1/` `tables[/{idOrName}]`, `transforms[/{idOrName}]` (`?import_table=` filters the list), `sources` and `auth-check`. Leave volatile values (row counts, last run times) out of discovery responses: the plugin saves them and compares them to detect changes.
- **No secrets or code.** A discovery response never contains token values, secrets or script bodies; scripts are reported as booleans only.
- **Choice values come back as stored** (lowercase, e.g. `validationType` `none` | `none_bearer_url` | `hmac_header` | `hmac_body`, `mappingType` `copy` | `lookup` | `lookup_multiple` | `transform`). Map them in the plugin. Inactive child records (e.g. webhook mappings) are included with `active: false`, and the plugin hides them; records without an `active` field are all shown. A reference that no longer resolves comes back with its `id` and null details (webhooks) or as `null` (imports).
- **Names can be shared.** Import tables, import sources and transforms are found by name across the whole instance, and runs fail when a name is used twice. The instance reports this as `nameShared: true` on each record (and `ambiguous: true` in the auth check). Use that flag, and never infer the rule by counting names in a list: the rule may change. Details answer 409 for a shared name, and `/` can't appear in a name in a path, so the editor reads a record picked from a list by its `id`. Keep the names on the node: the runtime sends names.
- **The instance answers an unauthenticated request with an empty-bodied 401.** Only a malformed `Authorization` header gets `{"_error":"Unauthorized"}`. Rely on the status code, not the body.
- **Minimum version.** The lookups and Test auth checks need Servicely 1.11.122 or later (`common.DISCOVERY_MIN_VERSION`). Build unsupported messages with `common.requiresVersion(what, fallback)`, and keep the version in the README requirements and the help's *Servicely version* section in step with it. A new lookup that needs a later version gets its own constant.
- **Optional.** An instance without the endpoint answers 404 or 405 without `_error`, succeeds without `data` (an older build serves its web app page), or answers 401 `{"loginRequired": true}` (the same web app, since requests send `Accept: application/json`), or answers `{"message": "No static resource ..."}` with any status (an older build without the route). The route returns these as `{error, unsupported: true}`, and the editor falls back to free-text entry. So every error from a discovery endpoint must carry `_error`, and its 401 must never be `{"loginRequired": true}`; 400/401/403/404/409 keep their status on the way to the editor. Node fields always accept typed values and `${msg.x}`, and the runtime never depends on discovery.
- **Saved as documentation.** A node may keep what it retrieved in a hidden `defaults` property (`webhook_info`, `import_info`, `import_source_info`, `transform_info`, each `{retrievedAt, data}`, via `ServicelyEditor.snapshot`), so it stays visible in the dialog and the Info sidebar when the instance can't be reached. Only what discovery returns is saved, since it ends up in flow files and exports. Drop it when the node's reference changes. Keep the old copy, and its date, when a refresh returns the same data, so the node isn't marked as changed. The runtime ignores it.
- **Editor rendering.** Build instance data into the DOM with jQuery `.text()`, never HTML strings.
- **Testing credentials from the dialog** (*Test auth*): register it with `common.registerAuthTest`, which POSTs them to an admin route (`needsPermission("<type>.write")`), never in a URL.
  - The browser sends the typed value. An unchanged password field sends `__PWRD__`; the editor substitutes the undeployed value it holds in `node.credentials`, and the runtime falls back to `RED.nodes.getCredentials(id)`.
  - Use `common.relayToEditor` for the upstream call.
  - The instance endpoint must check credentials without side effects: never "test" by calling the real endpoint.
  - The instance checks the credential as the real endpoint would, including a token's URL Allowed Paths (the import auth check is evaluated as `/controller/ImportManager`), so a token limited to that endpoint can run it.
- **Specify before depending.** A new instance endpoint is first written up as a backend handoff document under `docs/internal/` (git-excluded, never committed). Specs stand in for it with `test/helpers/mock-server.js` and test the route through `createAdminServer(helper).request()` (`test/helpers/admin-server.js`), never `helper.request()`. That starts and closes a server on a new ephemeral port for every request, which made the full suite flaky: requests occasionally reached another test's server.
